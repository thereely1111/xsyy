## 什么是代码更新？

**简单理解**：代码更新就是把你在本地电脑上修改好的代码，上传到服务器上，让服务器运行新版本的代码。

**举个例子**：
- 你在家里（本地电脑）写了一篇文章（修改代码）
- 你需要把文章发到公司（服务器）让同事看到（用户访问）
- 这个过程就是"代码更新"或"部署"

## Git 基础概念

### Git 是什么？

**Git** 是一个"版本控制系统"，可以理解为：
- 📝 **代码的时光机**：可以回到任何历史版本
- 👥 **多人协作工具**：多人可以同时修改代码而不冲突
- 💾 **代码仓库**：所有代码都保存在一个地方（GitHub/GitLab）

### 基本概念

#### 1. **仓库（Repository）**
- 就是存放代码的文件夹
- 本地仓库：你电脑上的代码
- 远程仓库：服务器上的代码（GitHub/GitLab）

#### 2. **提交（Commit）**
- 就像"保存"按钮
- 每次修改代码后，需要"提交"才能保存
- 提交时会写一条说明，比如"修复了登录bug"

#### 3. **分支（Branch）**
- 就像"平行世界"
- 主分支（main）：稳定版本，用户看到的
- 开发分支（develop）：开发中的版本
- 功能分支（feature）：开发新功能时创建

#### 4. **拉取（Pull）**
- 从服务器下载最新代码到本地

#### 5. **推送（Push）**
- 把本地代码上传到服务器

## 分支策略详解

### 为什么需要多个分支？

**想象一下**：
- 你在写作业（开发新功能）
- 如果直接在作业本上写，写错了就改不回来了
- 所以你先在草稿纸上写（feature分支）
- 写好了再抄到作业本上（合并到main分支）

### 我们的分支结构

```
main (主分支)
  ↓
  ├─ develop (开发分支)
  ↓
  ├─ feature/新功能1 (功能分支1)
  ├─ feature/新功能2 (功能分支2)
  └─ hotfix/紧急修复 (紧急修复分支)
```

### 各分支的作用

#### 1. **main 分支（生产环境）**
- **作用**：用户实际使用的版本
- **特点**：非常稳定，不能有bug
- **部署到**：生产服务器（用户访问的服务器）
- **更新频率**：只有测试完全通过才更新

#### 2. **develop 分支（开发环境）**
- **作用**：开发人员测试的版本
- **特点**：可能有小bug，但基本可用
- **部署到**：开发服务器（内部测试）
- **更新频率**：每天或每次功能完成

#### 3. **feature 分支（功能分支）**
- **作用**：开发单个新功能
- **特点**：可能不完整，可能有bug
- **部署到**：不部署，只在本地开发
- **生命周期**：功能完成后删除

#### 4. **hotfix 分支（紧急修复）**
- **作用**：修复生产环境的紧急bug
- **特点**：快速修复，直接合并到main
- **部署到**：生产服务器
- **使用场景**：用户无法登录、服务器崩溃等

## 部署流程详解

### 完整流程图

```
1. 本地开发
   ↓
2. 提交到 feature 分支
   ↓
3. 合并到 develop 分支
   ↓
4. 自动部署到开发服务器（测试）
   ↓
5. 测试通过后，合并到 main 分支
   ↓
6. 自动部署到生产服务器（用户使用）
```

### 详细步骤说明

#### 步骤 1：本地开发

**你在做什么**：
- 在本地电脑上修改代码
- 比如：添加新功能、修复bug

**代码位置**：
- 本地电脑：`D:\nick\大模型应用工程师\XSYY`

**操作**：
```bash
# 1. 创建功能分支
git checkout -b feature/添加删除功能

# 2. 修改代码（用编辑器修改文件）

# 3. 提交代码
git add .
git commit -m "添加了删除功能"
```

#### 步骤 2：提交到 feature 分支

**你在做什么**：
- 把修改的代码保存到Git仓库

**操作**：
```bash
# 推送到远程仓库
git push origin feature/添加删除功能
```

**结果**：
- 代码上传到GitHub/GitLab
- 其他人可以看到你的代码

#### 步骤 3：合并到 develop 分支

**你在做什么**：
- 把功能分支的代码合并到开发分支

**操作**：
```bash
# 1. 切换到 develop 分支
git checkout develop

# 2. 拉取最新代码
git pull origin develop

# 3. 合并功能分支
git merge feature/添加删除功能

# 4. 推送到远程
git push origin develop
```

**结果**：
- develop 分支包含了你的新功能
- 触发自动部署到开发服务器

#### 步骤 4：自动部署到开发服务器

**系统在做什么**：
- GitHub Actions（自动化工具）检测到 develop 分支有更新
- 自动执行部署脚本
- 把代码部署到开发服务器

**你不需要做什么**：
- 系统自动完成

**结果**：
- 开发服务器运行新版本
- 可以在开发服务器上测试新功能

#### 步骤 5：合并到 main 分支

**你在做什么**：
- 测试通过后，把代码合并到主分支

**操作**：
```bash
# 1. 切换到 main 分支
git checkout main

# 2. 拉取最新代码
git pull origin main

# 3. 合并 develop 分支
git merge develop

# 4. 创建版本标签
git tag -a v1.0.1 -m "版本 1.0.1：添加删除功能"

# 5. 推送到远程
git push origin main
git push origin v1.0.1
```

**结果**：
- main 分支包含新功能
- 触发自动部署到生产服务器

#### 步骤 6：自动部署到生产服务器

**系统在做什么**：
- 检测到 main 分支有更新
- 自动执行生产环境部署脚本
- 备份当前版本
- 更新代码
- 运行数据库迁移
- 重启服务

**你不需要做什么**：
- 系统自动完成

**结果**：
- 生产服务器运行新版本
- 用户可以使用新功能

## 实际操作步骤

### 场景一：开发新功能

#### 第 1 步：创建功能分支

```bash
# 在项目根目录执行
cd D:\nick\大模型应用工程师\XSYY

# 确保在 develop 分支
git checkout develop
git pull origin develop

# 创建新功能分支
git checkout -b feature/添加AI问答功能
```

**解释**：
- `git checkout develop`：切换到开发分支
- `git pull`：下载最新代码
- `git checkout -b feature/xxx`：创建并切换到新分支

#### 第 2 步：开发功能

```bash
# 修改代码文件（用编辑器）
# 比如修改 backend/app.py

# 查看修改了哪些文件
git status

# 添加修改的文件
git add backend/app.py

# 提交修改
git commit -m "添加AI问答功能"
```

**解释**：
- `git status`：查看哪些文件被修改了
- `git add`：把文件添加到"暂存区"（准备提交）
- `git commit`：正式提交，保存修改

#### 第 3 步：推送到远程

```bash
# 推送功能分支到远程仓库
git push origin feature/添加AI问答功能
```

#### 第 4 步：合并到 develop（通过 Git 界面或命令行）

**方法一：使用 GitHub/GitLab 网页**
1. 打开 GitHub/GitLab 网站
2. 找到你的功能分支
3. 点击 "Create Pull Request"（创建合并请求）
4. 选择合并到 `develop` 分支
5. 点击 "Merge"（合并）

**方法二：使用命令行**
```bash
# 切换到 develop 分支
git checkout develop
git pull origin develop

# 合并功能分支
git merge feature/添加AI问答功能

# 推送到远程
git push origin develop
```

#### 第 5 步：等待自动部署

- 系统会自动部署到开发服务器
- 等待 2-5 分钟
- 在开发服务器上测试功能

#### 第 6 步：测试通过后，合并到 main

```bash
# 切换到 main 分支
git checkout main
git pull origin main

# 合并 develop 分支
git merge develop

# 创建版本标签
git tag -a v1.1.0 -m "版本 1.1.0：添加AI问答功能"

# 推送
git push origin main
git push origin v1.1.0
```

#### 第 7 步：等待自动部署到生产

- 系统会自动部署到生产服务器
- 等待 5-10 分钟
- 用户可以使用新功能

---

### 场景二：修复紧急bug

#### 第 1 步：创建 hotfix 分支

```bash
# 从 main 分支创建 hotfix 分支
git checkout main
git pull origin main
git checkout -b hotfix/修复登录bug
```

#### 第 2 步：修复bug并提交

```bash
# 修改代码
# 提交
git add .
git commit -m "修复登录bug"
git push origin hotfix/修复登录bug
```

#### 第 3 步：合并到 main（紧急）

```bash
git checkout main
git merge hotfix/修复登录bug
git push origin main
```

#### 第 4 步：自动部署

- 系统自动部署到生产服务器
- 用户问题解决

## 常见问题

### Q1: 如果部署失败了怎么办？

**A**: 系统会自动回滚到上一个版本
- 备份在 `/opt/xsyy/backups/` 目录
- 可以手动恢复

### Q2: 如何查看部署日志？

**A**: 
```bash
# 查看部署日志
tail -f /opt/xsyy/deploy.log

# 查看服务日志
sudo journalctl -u xsyy-backend -f
```

### Q3: 如何手动部署？

**A**: 如果自动部署失败，可以手动执行：
```bash
cd /opt/xsyy
./deploy/deploy.sh prod
```

### Q4: 如何回滚到上一个版本？

**A**:
```bash
cd /opt/xsyy
./deploy/rollback.sh
```

## 重要提醒

1. **永远不要直接修改 main 分支**
   - 必须通过 develop → main 的流程

2. **部署前一定要测试**
   - 先在开发环境测试
   - 确认没问题再部署到生产

3. **重要操作前要备份**
   - 数据库备份
   - 代码备份

4. **遇到问题及时回滚**
   - 不要硬撑
   - 先回滚，再排查问题
