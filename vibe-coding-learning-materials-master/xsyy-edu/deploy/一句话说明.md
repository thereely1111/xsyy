# 一句话说明 - 代码更新流程

## 🎯 最简单的理解

**代码更新 = 把本地修改的代码上传到服务器，让服务器运行新版本**

---

## 📝 完整流程（用最简单的话说）

### 日常更新代码（3步）

```
1. 在本地修改代码
2. 提交并推送到 GitHub
3. 系统自动部署到服务器（2-5分钟）
```

### 详细步骤

#### 步骤 1: 修改代码
- 用编辑器修改代码文件
- 保存文件

#### 步骤 2: 提交代码
```bash
git add .
git commit -m "添加新功能"
git push origin develop  # 开发环境
# 或
git push origin main     # 生产环境
```

#### 步骤 3: 自动部署
- GitHub Actions 自动检测到代码更新
- 自动执行部署脚本
- 2-5 分钟后，服务器运行新版本

---

## 🔄 两种方式

### 方式一：自动部署（推荐）⭐

**优点**：
- 简单：推送代码就自动部署
- 安全：有备份和回滚机制
- 快速：2-5 分钟完成

**怎么做**：
1. 配置 GitHub Secrets（只需一次）
2. 以后每次推送代码就自动部署

### 方式二：手动部署

**什么时候用**：
- 自动部署失败时
- 需要立即部署时
- 测试部署脚本时

**怎么做**：
```bash
# SSH 连接到服务器
ssh user@server

# 执行部署脚本
cd /opt/xsyy
./deploy/deploy-prod.sh
```

## 🎓 学习建议

### 如果你是小白

1. **第一天**：阅读 `快速开始.md`，完成第一次手动部署
2. **第二天**：阅读 `代码更新完整指南.md`，理解基本概念
3. **第三天**：配置 GitHub Actions，实现自动部署
4. **以后**：每次推送代码，等待自动部署

### 如果你有经验

1. 直接看 `快速开始.md` 的命令
2. 配置 GitHub Secrets
3. 开始使用

---

## ⚠️ 重要提醒

1. **生产环境部署前一定要测试**
   - 先在开发环境测试
   - 确认没问题再部署到生产

2. **遇到问题立即回滚**
   ```bash
   ./deploy/rollback.sh
   ```

3. **永远不要直接修改 main 分支**
   - 必须通过 develop → main 的流程

---

## 🆘 遇到问题？

1. 查看 `部署检查清单.md`
2. 查看脚本日志：`/opt/xsyy/deploy.log`
3. 查看服务日志：`sudo journalctl -u xsyy-backend -f`
